# 001 — 플랫폼 순서: 웹 우선 → Android TWA → iOS 네이티브 계층

- 상태: 승인 (2026-08-10)
- 결정자: PO
- 관련 지식: [context.md](../context.md) §4 마켓 심사 제약, §5 개인정보, §부록 ADR 안건

## 맥락

- 최종 목표는 구글 플레이·앱스토어 **양쪽 마켓 출시·배포 경험**이다 (프로젝트 정본 목표 — 변경 없음).
- 당면 목표는 프로토타입을 만들어 회사 동료에게 사용자 테스트·피드백을 받는 것이다.
- 개발자 계정이 양쪽 다 없다 (플레이 $25 1회, 애플 연 $99 — 아직 미지출).
- 포지셔닝은 재미(엔터테인먼트) 위주로 확정되어 있다 — 정확도 경쟁을 하지 않는다.

## 결정

플랫폼을 다음 3단계 순서로 진행한다.

1. **1단계 — 모바일 최적화 반응형 웹**: GitHub Pages에 정적 배포. 사진 분석은 전부 브라우저 안(클라이언트)에서 수행. 회사 동료 피드백 수집 채널.
2. **2단계 — Android**: TWA(Trusted Web Activity — 웹을 Play 스토어 앱으로 등재하는 공식 경로)로 출시. 개인 계정의 비공개 테스트 요건(테스터 12명 × 14일 연속)은 1단계 피드백에 참여한 동료들로 충족한다.
3. **3단계 — iOS**: 웹 래핑만으로는 가이드라인 4.2(최소 기능) 반려 위험이 있으므로, 네이티브 계층(자체 내비게이션·푸시·오프라인 처리 등)을 얹어 대응한다.

## 근거

- GitHub Pages는 HTTPS 정적 호스팅 → 브라우저 카메라 권한(getUserMedia)이 동작한다.
- 서버가 없어 사진이 이용자 기기를 떠나지 않는다 → 사업자 관점에서 개인정보 **"수집" 자체가 발생하지 않는 구조** (context.md §5). '분석 후 즉시 폐기'보다 강한 설계이며, 애플 5.1 권한 심사 대응 논리로도 재사용된다.
- 비용 0으로 프로토타입 → 사용자 테스트(당면 목표)까지 도달 가능. 계정 등록비는 각 마켓 단계 진입 시점까지 이연된다.
- Android는 TWA라는 공식 경로가 있어 웹 재사용 부담이 작고, iOS만 네이티브 계층 추가 작업이 필요하다 — 부담이 작은 순서대로 배치했다.

## 결과 (트레이드오프)

- 마켓 출시 경험은 뒤로 밀린다. 목표 자체는 유지 — 웹은 최종장이 아니라 1단계다.
- 결과 저장·공유·이력 등 서버 저장 기능을 넣는 순간 "수집 없음" 구조가 깨진다 — 그런 기능 추가 시 context.md §5 재검토가 선행 조건이다.
- iOS 단계는 연 $99 + 네이티브 계층 개발 비용이 확정적으로 발생한다.
- 기술 스택 선택(ADR-002)은 "1단계 정적 웹 배포와 충돌하지 않을 것"이 제약 조건이 된다.
