# 005 — 결과 카드: canvas 직접 렌더링, 카드에 사진을 담지 않음

- 상태: 승인 (2026-08-16)
- 결정자: PO
- 선행 결정: [002 웹 스택](002-web-stack-vite-react-mediapipe.md), [003 백엔드 없음](003-no-backend-phase1.md)
- 관련 지식: [context.md](../context.md) §5 얼굴 이미지 개인정보
- 구현: `src/components/result/cardImage.ts`

## 맥락

결과를 이미지로 저장하는 기능은 MVP의 필수 항목이다 — 공유·확산이 재미 포지셔닝의 핵심이라 결과를 보고 끝나면 루프가 닫히지 않는다.

만드는 방법은 크게 둘이었다.

1. **DOM 캡처** — 화면에 이미 그려진 결과 영역을 라이브러리(html2canvas 등)로 이미지화한다. 화면과 이미지가 자동으로 같아진다.
2. **canvas 직접 렌더** — 저장용 이미지를 코드로 따로 그린다.

또 하나 정할 것이 있었다. 분석에 쓴 얼굴 사진을 카드에 넣을 것인가.

## 결정

- **canvas 2D로 저장용 이미지를 직접 그린다.** DOM 캡처 라이브러리를 쓰지 않는다. 카드 크기는 1080×1350(4:5)으로 고정한다.
- **카드에 얼굴 사진을 넣지 않는다.** 타입·팔레트·염색·얼굴형·컷 제안과 고지 문구만 담는다.

## 근거

**직접 렌더를 고른 이유**

- DOM 캡처는 새 런타임 의존성을 들인다. 이 프로젝트의 런타임 의존성은 지금 React와 MediaPipe뿐이고, 배포 대상이 정적 파일뿐이라는 단순함(ADR-003)이 강점이다. 카드 하나 때문에 이 구조를 늘릴 이유가 약했다.
- 화면 레이아웃과 공유 이미지의 **요구가 애초에 다르다.** 화면은 세로로 긴 모바일 뷰포트에 맞춰 스크롤되지만, 공유 이미지는 잘리지 않는 고정 비율이어야 한다. 자동으로 같아지는 것이 이 경우에는 이점이 아니다.
- 캡처 라이브러리는 CSS 지원 범위·폰트 로딩 타이밍에 따라 결과가 달라지는 실패 모드가 있다. 직접 그리면 출력이 결정적이다.

**사진을 넣지 않은 이유**

- 저장된 파일은 사용자가 공유하는 순간 기기를 떠난다. 여기에 얼굴이 담기면 "사진이 기기를 떠나지 않는다"는 고지(ADR-003, context.md §5)의 취지가 사용자 입장에서 흐려진다. 기술적으로는 사용자가 스스로 공유하는 것이라 고지가 거짓이 되지는 않지만, **고지의 취지를 지키는 쪽**을 택했다.
- 얼굴이 없는 카드가 공유 문턱도 낮다. 결과만 담긴 이미지는 그대로 단체 대화방에 올릴 수 있다.

## 결과 (트레이드오프)

- **카드 레이아웃과 화면 레이아웃이 별도 코드다.** 항목을 추가하면 두 곳을 함께 고쳐야 하고, 한쪽만 고치면 화면과 저장 이미지가 어긋난다. 이 중복은 인지하고 받아들인 비용이다 — 항목 수가 더 늘면 표시 데이터를 한 곳에서 만들고 두 렌더러가 소비하는 형태로 정리할 여지가 있다.
- 텍스트 줄바꿈·좌표를 직접 계산해야 한다. 지금은 한국어를 음절 단위로 끊는 단순한 방식이며, 문구가 길어지면 카드 아래쪽이 넘칠 수 있다.
- `roundRect`를 쓰므로 아주 오래된 Safari(16.4 미만)에서는 카드 생성이 실패한다. 실패는 예외로 잡아 "화면을 캡처해 주세요" 안내로 대체하며, 앱의 다른 기능은 영향받지 않는다.
- 사진을 원하는 사용자에게는 카드가 밋밋할 수 있다. 실기기 피드백(Phase 5)에서 사진 포함 요구가 실제로 나오면 재검토 대상이다 — 그때는 이 결정의 개인정보 근거를 함께 다시 본다.
